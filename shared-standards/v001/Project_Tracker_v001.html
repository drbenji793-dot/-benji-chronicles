Execution rules

  1. Define the machine. Record the target site, purpose, live baseline, shared tools, authorized scope and completion criteria. Use this tracker framework for any site; keep its project tasks separate from the reusable rules.
  2. Test with real content. Use existing stories, books, tasks or records to reproduce faults and evaluate displays, questions, answers, critique, connections and exports. Real content is valid test material; fixing its meaning is not the assignment.
  3. Fix the underlying tool. Correct the shared behavior so it works for all relevant existing records and future content. Do not substitute a one record content edit for a system fix.
  4. Preserve content. Use copies or isolated test records when testing actions that modify data. Changes to real content require separate explicit authorization. Inspect live content without rewriting names, answers, plots or prose.
  5. Verify the full result. Check saving, reopening, connected views, exports, data preservation and mobile behavior as applicable. Record evidence, source revisions and the actual tested environment. Desktop checks do not establish iPhone Safari acceptance.
  6. Separate the work. Track software defects, content issues and author decisions separately. Park editorial issues outside website completion criteria. A content example may reveal a tool defect without authorizing correction of that content.
  7. Finish main work first. Prioritize core functions, connected workflows, then cleanup and verification. Continue every authorized task that can proceed independently.
  8. Decide routine details. Use professional judgment for reversible implementation choices within the approved scope. Do not stop after small task batches to request permission already given.
  9. Park major decisions. Record the exact blocked item, its dependencies and why author input is needed. Skip only the dependent work and continue everything else. Do not guess approval.
  10. Collect one decision batch. Deduplicate questions and major decisions and present them together after the main executable work is finished. Each question includes a recommended answer, clear alternatives and the effect of each option.
  11. Interrupt only when necessary. Interrupt early only for immediate risk of data loss, an irreversible action needing authorization, or a blocker that prevents all remaining useful work. Explain the concrete reason.
  12. Report honestly. Keep implementation, verification, publication and author decisions separate. Record assumptions and remaining limitations. Silence is never approval. Progress updates do not require a response.

Completion gate

  1. Every criterion has evidence from the relevant environment.
  2. Content hashes or equivalent preservation checks match where required.
  3. Build and relevant workflow checks passed.
  4. Publication is verified separately from implementation.
  5. Actual iPhone Safari checks remain open until performed.
  6. Recovery status describes exactly what is saved and what was tested.
  7. Outstanding questions and next work are delivered together.
